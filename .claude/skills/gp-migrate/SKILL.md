# 汎用プローブへの移行（Lua とアセンブリの相互変換）

`VehicleCalcModel/GeneralProbe/` の仮想機械（仕様は `BYTECODE_SPEC.md`）と、Lua のマイコンのあいだでロジックを移す作業の手順である。
手順の順序には理由がある。理由を書いたので、書かれていない場面では理由から考えてよい。

## 先に決めること

### 移すかどうか

安定していて変える予定のない Lua は、移さずに実機へ Lua のまま載せるのが自然である。
仮想機械に載せる動機は「マイコンを触らずにロジックを差し替えたい」ことなので、移すのは、調整・実験・新しい制御則を試す部分に限る。
1800系のコアの移植は、仮想機械の能力を確かめるための実験であり、本番に載せるためではなかった。

### 方向と正本

| 方向 | 使う場面 |
|---|---|
| Lua → アセンブリ | 既存のロジックを、注入で差し替えられるようにしたい |
| アセンブリ → Lua | 仮想機械で詰めたロジックを、実機投入用の Lua に固めたい（速さ、安定、注入の経路が要らない） |

変換の前に、**変換後に人が直す側（正本）はどちらか**を決める。
決めずに両方を直すと、どちらが正しいか分からなくなる。生成物の側は直接直さず、正本を直して作り直す。

## 手順

### 1. 現状を把握する

- 元の実装の正本、既存のテスト、比べられる境界を確かめる。
- 境界は **配備される形の外側**にそろえる。関数の境界だけで比べると、配備形がその外側で行う処理（状態の float32 への丸め、同期の再計算など）を取りこぼす。
  1800系では `core_tick` の境界と、`state_sync` を含む `onTick` の境界（composite の 32 入力 32 出力）の両方で比べた。
- `state_sync` のように配備形が外側で行う機構は、仮想機械に組み込まず、**バイトコードのプログラムとして書く**（利用者の方針）。

### 2. 移行テストを確保する

移行テストは、変換の前に用意する。後から書くと、出来上がったものに合わせて書いてしまう。

- 既存のテストがあれば、それを使う。変換後に差し替えて流せる形にする（例: グローバルの `core_tick` を差し替える。`test/chuso1800_port.lua`）。
- なければ書く。元の実装を基準（正解）にして、次を含める。
  - 乱択の入力（通常の範囲）。
  - **境界を狙った入力**: 実装が比べているしきい値の直前・直後・ちょうど。乱択では境界に当たらない。1800系では、速度 3 m/s のしきい値の変更が、一様な乱択では検出できなかった。
  - 状態を持つ場合は、複数 tick の連続（乱択の歩行）。外から状態が書き換わる機構があれば、その事象も混ぜる。
  - 実運用に近い軌道。
- 比較の基準は元の実装の出力である。**テストが正しいことの確認**として、まず元の実装でテストを流し、通ることを確かめる。

### 3. 変換する

- 関数・節の単位で分け、元の名前を保つ。追跡できるように、ファイルや節を元の関数に対応させる。
- 浮動小数点の演算は、**元と同じ順序**で行う（結合の向きまで）。順序が違うと、最後の桁がずれて、境界の判定がまれに変わる。
- 論理は 0/1 のセルで持つ。Lua の `and`/`or` が値を返す書き方（`a and b or c`）は、値の意味が変わらないか確かめて、条件の選択（`SEL`、`CMOV`）に直す。
- 定数は元の式のまま写す（アセンブラの `#(1.00-0.30)` のような定数式が使える）。手で計算した値を書かない。
- 元の実装に奇妙な点（名前と内容の食い違いなど）を見つけても、**移行の中で直さない**。そのまま移し、見つけたことを記録する。直すのは別の判断である。
- アセンブリ → Lua の方向は、`LUA_CODING_GUIDE.md`（グローバル関数、位置引数、`dofile` でフラット化）に従い、`pnpm microcontroller build` の文字数の検査まで通す。この方向は実績がなく、手順は未検証（unconfirmed）である。

### 4. 元と変換後の両方で、同じテストを流す

- 通常の入力と、**異常入力**を、**両方**で流す。異常入力は、元の実装が想定していない入力のことである。
  - NaN、無限大、範囲外、負、巨大な値、0 による除算。
  - 状態の不正な値（範囲外のカウンタ、あり得ない組み合わせ）。
  - 仮想機械側では、予算の打ち切り、範囲外の番地、ポート番号の折り返し。
- 異常入力での結果は、次のどちらかに分類して記録する。
  - **同じ結果**になる。
  - **違う結果**になるが受け入れ可能。例: 元はエラー（または NaN）になるが、仮想機械は全域的で決まった値を返す。理由を付けて記録する。
- 分類できない違いは、受け入れ可能とは言えない。人に返す。

### 5. テストの検出力を確かめる

- 一度で全部通ったら、疑う。変換後の定数やしきい値を 1 つずつ変えて（突然変異）、テストが落ちることを確かめる。
- 落ちない変更は、テストの穴か、等価な変更（結果が変わらない変更）である。
  - 穴なら、境界を狙う入力を足す。足せないなら、穴として記録する。
  - 等価な変更は、等価である理由を書く（1800系の `s2` を更新しない変更は、フィードバックが整合している限り同じ結果になるので等価だった）。

### 6. 実測する

- 仮想機械: 1 tick の命令数（`gp_instr()`）、時間。時間は開発 PC の値であり、実機の値ではない。
- Lua: minify 後の文字数（8192 が上限）。
- 実測できなかった項目は、何を実行しなかったかと理由を書く。

### 7. 受け入れを判断する

次をすべて満たしたとき、受け入れ可能として完了する。

1. 元でテストが通る。
2. 変換後で、通常の入力が元と一致する（許容誤差を決めたなら、その値と理由を書く）。
3. 異常入力のすべてが分類され、違いは受け入れ理由が書かれている。
4. 突然変異の結果が記録されている（落ちたもの、穴、等価なもの）。
5. 実測値（命令数と時間、または文字数）が記録され、上限の内側にある。
6. 未検証の事項が、`verified` / `inferred` / `unconfirmed` の確度で明記されている。

受け入れの判断は、書かれた記録から第三者が追えるようにする。理由が書けない違いが残るなら、完了とせず人に返す。

## 記録の置き場所

移した先のディレクトリ（例: `programs/<名前>/`）の README に、次を書く。

- 元の実装の場所と、比較した境界。
- 一致の範囲（試行回数）と、受け入れた違い。
- 突然変異の結果と、残った穴。
- 実測値と、未検証の事項。

## 注意

- 配列は `.vars` で連続したセルとして確保し、`@name_1` を基点に `LD`/`ST` で引く。
- float32 のビットパターンを扱うセルは、NaN や無限大のビットを変えない命令（`MOV`、`LD`、`ST`、`CMOV`、`F2I`、`PST`）だけで運ぶ。計算する命令は NaN を 0 として読む。
- ゴールデンファイルの再生成や、失敗するテストを緩めて通すことは、修正ではなく判断である。人が内容を見て承認していない出力を、正としない。
- テストの出力の整理（長い差分の要約など）は、安いモデルに任せてよい。変換そのものと、受け入れの判断は、強いモデルが行う。
