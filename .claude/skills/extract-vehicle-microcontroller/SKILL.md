# ビークルからのマイコン抽出

ビークルXMLの中のマイコンを取り出して、storm-mcl のプロジェクト（`project.json` と `.sw-net`）に起こす手順である。
取り出しから検査までを付属の `extract.mjs` が一気に行う。出力はスクラッチパッドに作り、リポジトリには何も置かない。

## 手順

1. `extract.mjs` を実行する。生のXMLは先に読まない。
   ```
   node .claude/skills/extract-vehicle-microcontroller/extract.mjs <vehicle> <名前 | --at body,x,y,z> --out <スクラッチパッド内のディレクトリ>
   ```
   - `<vehicle>` は `vehicles/` からの相対パスで、拡張子は省ける（例: `CHUSO2000/CHUSO2000_2001`）。
   - マイコンは、ビークル内の名前（完全一致）か、`--at` の位置（`body` の `unique_id`、`vp` の x,y,z）で指す。同名が複数あるときは先頭を使い、定義が何種類あるかを出力に示す。名前が分からないときは、わざと間違った名前を渡せば、ビークル内の名前の一覧がエラーに出る。
2. 出力の要約を読んで、結果を報告する。判断の材料は、要約と storm-mcl の診断だけでよい。
   - ノード数、部品数、Lua の本数、部品の種類。
   - `check-dsl` と `typecheck-dsl` の合否、storm-mcl の警告（`XML_IMPORT_EMPTY` など）。
   - 抽出物に含まれる property の値（個体差の有無が分かる）。
   - `EMPTY:` と出たときは、中身がない。
3. リポジトリに置くかを、利用者に聞く。空のときは、置かずに「空」と答える。置き場所の名前や `SPEC.md` は、頼まれていなければ決めない。

## 理由

- **生のXMLを読まない。** ビークルXMLは1行で約2MBあり、読んでも判断の材料にならない。ツールの出力のほうが、確度が高い。
- **`sourceName` を直す。** storm-mcl の出力には一時ファイルの絶対パスが入る。ほかのプロジェクトに合わせて単体のファイル名に直してある。

## 注意

- 抽出物には、ビークルの property の値（例: `Door Side` の `i=1`）が入る。個体ごとに違う値は、プロジェクトに持たせず、差し替えの際に注入する方針である（`AGENTS.md` の「ビークルXMLへのマイコン差し替え」）。抽出物から取り除くかどうかは、利用者に聞く。
- ビークルの定義は、`parseVehicleXml` が読める範囲でしか取り出せない。読めないビークルは、エラーで止まる。
- ビークルのマイコンには、制御用でない装飾用ブロックが含まれることがある。中身がない場合は抽出結果を保存しない。
- 取り出したプロジェクトに `/rename-and-sort` を使ってよいのは、ノードがある場合に限る。空には使わない。
